# 惰性唤醒与定向发言

## Status
accepted

## Context
多设备协作里最贵的资源是"唤醒一个 agent 跑一轮模型"：既花 token，也占用该设备用户的时间与注意力。广播式协作会唤醒不必要的 agent，导致重复工作与互相打断。

## Decision
- **按需唤醒**：只有被点名（Addressing）或被分配 Task Block 的 agent 才被唤醒；未点名成员不启动、不跑模型。
- **Participant agent 惰性创建**：加入房间时只建立成员记录与只读 Board 镜像；该成员第一次被点名/领取任务时才创建它的本地会话并注入 Participant Brief。直调工具不经过 agent，走 Execution Slot。
- **广播不是默认行为**：`*` 需要显式授权/确认（受 Room Policy 约束）。
- **定向发言**：任何成员都可以向任意一个或多个成员说话；相同内容发给多人 = 一条带收件人集合的消息；对每个成员说不同的话 = 多条消息（可用一次批量调用按顺序追加，保持审计与顺序）。
- 离线成员的消息持久在 Host 日志；唤醒是尽力而为，成员回归时按"自上次已读"补摘要（离线投递细节待定）。

## Considered Options
- 全员广播、每条消息唤醒所有成员——token 与注意力最差，否决。
- 加入房间即创建每个成员的 agent——房间多几个不活跃成员就多几个空闲会话，否决。
- 由发件人本地转发、不经 Host——没有统一顺序与审计，否决。

## Consequences
首次唤醒多一次会话创建成本；协议需要 wake/assignment 事件与 turn/end 上报；批量定向消息要保证顺序与可审计；Room Policy 需要约束广播权限。
