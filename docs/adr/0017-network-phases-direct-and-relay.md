# 网络层分阶段：v1 直连、v2 自建 Relay，先不做 P2P 打洞

## Status
accepted

## Context
设备可能在同一局域网，也可能在不同网络。远程软件（UU 远程等）的通用原理是"信令 + NAT 打洞 + Relay 兜底 + 端到端加密"，但我们传输的是 RPC、消息与任务状态，不是低延迟视频流：中继兜底已经够用，自研 NAT 打洞成本高、调试 NAT 场景耗时。

## Decision
网络层分阶段实现：
- **v1（本期）**：局域网/Overlay 直连。手动地址 + UDP 广播发现；跨网由用户已有的 Tailscale/WireGuard 等提供可达性。设备身份 = Ed25519 静态密钥 + 邀请携带的 fleetKey；安全通道 = X25519 ECDH + HKDF + AES-256-GCM 帧；所有业务帧端到端加密。
- **v2（本期）**：自建轻量 Relay。控制通道用 fleetKey HMAC 注册与鉴权；数据面是 Relay 拼接的两条 TCP（只搬密文），两端在拼接字节流上跑同一套安全通道；**不实现 NAT 打洞**。
- **v3（后续可选）**：P2P 打洞优化，真需要低延迟时再做。

## Considered Options
- 一步到位自建完整"信令 + 打洞 + 中继"——工作量最大，否决。
- 长期只依赖第三方 overlay——用户需要装 VPN，否决为长期方案（可作 v1 跨网兜底）。
- 集成 libp2p/WebRTC——依赖重、Node 端调试成本高，暂不采用。

## Consequences
Relay 只能看到密文与元数据，必须"可信可用、不可读"；没有 NAT 打洞时跨网流量走中继有延迟与带宽成本；协议从 v1 起就带版本号与能力协商，便于后续加打洞。
