# ADR-0040：阈值模型选择——M-of-N 多签，不引入未审计 FROST

- **状态**：已决策（2026-11-18，1.20.1）
- **相关**：ADR-0028、ADR-0032、ADR-0038、ADR-0039

## 决策

- checkpoint 使用 **head 绑定的 M-of-N 多签名证书**：每个设备独立 Ed25519 签名，接收方按 roster 验签，只有同一 `seq+head` 的不同设备签名才计数；达到 `rotation.checkpointQuorum` 才写入信任。
- 不把 M-of-N 称为 FROST/阈值签名。
- 不引入手写 FROST、BLS 或 BFT 共识。

## 原因

1. **没有共享组密钥**：当前信任模型是每台设备用自己的身份密钥签名；FROST 需要组公钥、DKG/可信 dealer、份额刷新和 nonce 仪式。引入它会改变身份模型，而不是替换一个函数。
2. **本地信任不是共识**：每台设备独立验证同一 checkpoint 的签名集合；“多数设备签名”已经提供 M-of-N 授权。跨设备 BFT 共识解决的是“离线设备对同一日志顺序达成一致”，当前 Room/rotation 链另有机制。
3. **安全成本**：未审计的阈值签名实现比 M-of-N 更危险；错误会在“看起来验证通过”时静默丢失安全性。
4. **可验证性**：M-of-N 证书可以直接用现有 roster 公钥逐条验证，测试与审计成本低。

## 若未来必须 FROST

需要单独立项：

- 选定并审计密码学库（含 Ed25519/BLS 阈值实现）；
- 定义 DKG/reshare、份额存储、nonce 复用防护；
- 定义组公钥与现有 deviceId/roster 的关系；
- 提供迁移与回滚，不与 M-of-N 混用同一 trust 字段。

## 后果

- 正式发布说明必须明确“M-of-N 多签，不是阈值签名/BFT”。
- 若产品要求“单一固定组签名”或“跨主机强一致日志”，当前设计不满足，不能以发布掩盖。
